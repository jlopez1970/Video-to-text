# Video-to-Text — App State

Lives alongside the app in this folder. Updated by Claude every time the app changes, so
anyone (including a future Claude session) can see what this app does and why it's built
this way without needing the original chat.

## What this app does
Takes a video link L, downloads it into a local folder A ("repository A") using yt-dlp,
transcribes it with OpenAI Whisper, and saves the transcript into a local folder B
("folder B") as TXT (plain text) and/or WebVTT (timestamped subtitles). It also still
accepts a local MP4/MP3 file or a folder of them directly, skipping the download step.
A third step, Correct, then fixes recurring Whisper mis-hearings in those transcript
files (TXT/VTT/SRT/MD/DOCX) using a glossary built for this instructor's trading-class
recordings. PDF was considered and intentionally left out (see changelog).

## Files in this folder
- `version.py` — **no longer a source of truth** (changed 2026-08-28, see Version section
  below). Each of `vtt.py`/`transcript_corrector.py`/`gui.py` now carries its own
  independent `__version__`; this file is just a documentation-only registry showing all
  three at a glance plus a combined changelog. Nothing imports from it.
- `vtt.py` — core logic + CLI entry point (Download + Transcribe).
- `transcript_corrector.py` — Correct step: glossary-based text substitution.
- `correctionglossary.md` — reference doc explaining every correction mapping.
  - `is_url(text)` — detects whether the input is a link vs a local path.
  - `download_video(url, repo_dir)` — downloads via yt-dlp into repository A.
  - `resolve_media_files(input_path, repo_dir)` — figures out which file(s) to transcribe
    (download a URL, list a directory, or use a single file).
  - `prepare_model(model_name, lang, translate, engine="auto")` — loads Whisper. Since
    vtt.py 1.6.0 (2026-10-27): engine "mlx" (mlx-whisper, Apple MLX), "torch"
    (openai-whisper on MPS/CPU), or "auto" (MLX if installed, else torch; falls back to
    torch if MLX can't start or fails on a file). CLI `-e/--engine`; GUI always uses auto.
    Motivation: on a 4h class (medium, main narrator) transcription took 39m vs diarization
    13m, so Whisper is the bottleneck. Confirmed working on the Mac 2026-10-27.
    Since vtt.py 1.6.1 (2026-10-27): options set `condition_on_previous_text=False` (both
    engines) -- the default (True) let one bad segment seed a repetition loop ("y el
    outlook" x308, ~10 min lost + 113 empty cues on the 4h M4 class). Confirmed fixed on a
    re-run. Follow-up: skip VTT cues with no letters/digits (17 "."-only cues remained).
  - `process_file(media_path, model, options, outdir, formats)` — transcribes one file,
    writes `.txt` and/or `.vtt` into folder B.
  - `run_job(...)` — orchestrates all of the above. Shared by both the CLI and the GUI so
    they never drift out of sync.
  - `main()` — thin CLI wrapper (argparse) around `run_job`.
- `gui.py` — Tkinter desktop GUI with two independent tabs, each its own background
  thread + log panel: **Download** (link -> folder A, calls `vtt.download_video`) and
  **Transcribe** (any folder -> folder B as TXT/VTT, calls `vtt.run_job`, with a file
  picker to transcribe one file or all files in the folder).
- `readme.txt` — setup instructions (ffmpeg, whisper/torch/yt-dlp, python-tk) and usage
  for both the GUI and the CLI.
- `settings.json` — auto-generated by `gui.py`. Remembers the last-used link/path,
  repository A, folder B, language, model, output format, and translate checkbox, so the
  GUI reopens prefilled with your last run's values. Safe to delete if you want a clean slate.
- `app-state.md` — this file.

## Key decisions
- Downloader: yt-dlp (broad site support, actively maintained).
- Output: both TXT (plain, no timestamps) and VTT (timestamped) by default; selectable
  via `-f/--format` (CLI) or the Output format dropdown (GUI).
- Repository A and folder B are always explicit parameters (`-A/--repo`, `-B/--outdir`,
  defaulting to `./repository_A` and `./folder_B`), never hardcoded.
- Runs locally on this Mac (Apple M3, MPS acceleration) inside a venv with Homebrew
  Python. The Claude cloud session that builds/edits this code cannot execute it directly
  (no torch/whisper/tkinter there) — changes are verified there by syntax-checking plus
  running the logic end-to-end against stubbed torch/whisper/tkinter before being written
  here.
- GUI: Tkinter, chosen over a Streamlit web app for zero extra dependencies beyond
  `python-tk`, with background-thread execution so downloading/transcribing doesn't
  freeze the window.
- Parameter memory: GUI prefills last-used values on startup and saves on every Start
  click (chosen over a multi-entry link history dropdown).

**2026-10-27 — speaker filter ~50x slowdown fixed (untested on the Mac)** (`speaker_filter.py`
1.0.1 -> 1.1.0, `vtt.py` 1.5.0 -> 1.5.1). User reported "Main narrator only" made the process

before diarizing, and logs "Transcription took ..." / "Diarization took ... (audio length ...)".
Stub-tested (MPS success + MPS-failure->CPU retry). torch 2.13 was NOT changed by the pyannote
install (dist-info dates), so Whisper itself is still on MPS. Not committed to git.

- 2026-08-21 — Investigated user report of ~24GB memory usage. Confirmed via Q&A: happens
  during Transcribe, with the `large` Whisper model. Root cause is external to our code:
  on Apple Silicon's MPS backend, `large` can use well beyond its ~3GB of weights (often
  15-25GB+) because MPS often falls back to 32-bit math for ops Whisper uses, and its
  caching allocator (default `PYTORCH_MPS_HIGH_WATERMARK_RATIO` = 1.7x recommended working
  set) holds freed GPU buffers instead of returning them to the OS -- which shows up as
  regular RAM since Apple Silicon shares one memory pool. Changes made:
  - Added `vtt.release_gpu_memory(log=None)`: `gc.collect()` + `torch.mps.empty_cache()`
    (guarded by `is_available()`, safe no-op on non-MPS). Called between files during a
    batch run (so usage doesn't climb file-over-file) and once after every job finishes
    (drops the model too, via `del model`).
  - `prepare_model` now logs an explicit warning when `model_name` starts with "large",
    explaining the MPS memory behavior and suggesting `medium` as a lighter alternative.
  - `readme.txt` gained a "3B. MEMORY USAGE" section documenting the cause, what the app
    already does, and two optional env vars the user can set before launching:
    `PYTORCH_MPS_LOW_WATERMARK_RATIO` (lower it, e.g. to 1.0, to make PyTorch garbage-
    collect more proactively during a run) and `PYTORCH_MPS_HIGH_WATERMARK_RATIO` (lower
    it, e.g. to 1.0, for a hard cap at the recommended working set -- trades runaway growth
    for a possible OOM error, so best paired with a smaller model rather than used with
    `large` alone). Verified the exact semantics/defaults of both env vars against the
    PyTorch docs (docs.pytorch.org/docs/2.8/mps_environment_variables.html) before writing
    this guidance, since an earlier draft had the direction backwards.
  - Not yet confirmed by the user whether memory usage actually drops after this change --
    follow up if they report back.
